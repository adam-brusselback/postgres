# Profiling `suppress_redundant_updates_trigger`

CPU profile of `suppress_redundant_updates_trigger()` across several UPDATE
workloads, with flamegraphs, to find optimization opportunities.

**Headline:** the comparison the trigger exists to perform is essentially free
(~1% of the trigger's own cost). Almost all of the cost of attaching this
trigger is the generic BEFORE-ROW-trigger machinery around it, and roughly
70% of it is a single thing: the mandatory `heap_lock_tuple()` on the old
tuple, which happens *before* we can know the update will be suppressed.

---

## 1. Method

* Source: this tree (`20devel`), built `-O2 -g -fno-omit-frame-pointer`,
  asserts off, so frame-pointer stacks are complete and symbolized.
* `perf record -F 999 --call-graph fp` attached to the single pgbench backend
  for 30 s of a 40 s run; flamegraphs via Brendan Gregg's FlameGraph.
* Server: `shared_buffers=1GB`, `fsync=off`, `synchronous_commit=off`,
  `full_page_writes=off`, `autovacuum=off`. All tables fit in shared buffers,
  so every workload is CPU-bound and in-memory — that is deliberate, it puts
  the trigger's CPU cost under a microscope rather than hiding it behind I/O.
* 4 vCPU container, single client (`-c 1`), so the profile maps to one backend.

### Tables

| table | shape | size | notes |
|---|---|---|---|
| `t_narrow_*` | 4 cols | 5 MB / 100k rows (~52 B/row) | updates are HOT-eligible |
| `t_wide_*` | 62 cols | 87 MB / 100k rows (~870 B/row) | no TOAST; stresses memcmp/form_tuple |
| `t_idx_*` | 5 cols + 3 secondary indexes | 100k rows | a real update cannot be HOT |

Each shape exists twice — `_trig` (with the trigger) and `_notrig` (without) —
so every number is a paired comparison.

### Workloads

* **redundant** — `SET a = a, b = b`: NEW is byte-identical to OLD, so the
  trigger suppresses every update. Best case for the trigger.
* **changing** — `SET a = a + 1, b = b + 1`: the trigger can never suppress,
  so it is pure overhead. Worst case.

Both the simple query protocol and `-M prepared` were measured. Under the
simple protocol ~20-25% of backend CPU is parse+plan, which dilutes the
executor signal; the prepared numbers are the ones to reason about.

### A note on percentages

Raw "% of all samples" understates everything, because with one client the
backend spends ~20% of its samples in the scheduler/socket path
(`finish_task_switch`, `_raw_spin_unlock_irqrestore`) waiting for pgbench.
Unless stated otherwise, percentages below are **normalized to in-query
backend CPU** (the `exec_simple_query` / `exec_execute_message` subtree).
